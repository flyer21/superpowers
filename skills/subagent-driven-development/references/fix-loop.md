# 修复波

属于 superpowers:subagent-driven-development。整分支自审报告规格 ❌、关键或重要发现，或你确认为真正缺口的 ⚠️ 项目。

在修复波开始之前，两条路线立即离开它：

- 在进行时记录次要发现到进度账本（`任务 <N>: 次要（延后）: <一行摘要>`），并指向收尾的自审清单，以便它可以分类哪些必须在合并之前修复。没人阅读的汇总是一个无声丢弃。次要发现永远不进入修复波。
- 标记为计划强制的发现——或与计划文本要求的任何发现冲突——由你裁决：权衡发现与计划文本，以规格为绑定权威决定，并在你行动之前在账本记录裁决。不要因为计划强制而驳回发现，不要在没有记录裁决的情况下派遣与计划矛盾的修复。

其他所有东西进入修复波。一轮修复波是一次修复派遣加一次你自己的限定范围复检。**整条分支最多三轮**：

**第 1-2 轮——恢复原始实现者。** 逐字发送它开放发现。它的上下文完整：它知道任务、代码和它自己的选择。如果你的线束无法向活动子代理发送另一条消息，派遣新鲜实现者携带简报路径、账本路径和发现——账本是任一方式的持久记忆。

**第 3 轮——在更有能力的模型上派遣新鲜实现者**（根据 SKILL.md 的模型选择），带有简报路径、账本路径、开放发现和此框架："先前实现者尝试此任务 [N] 次；你现在拥有它。阅读账本了解尝试的内容。"存活两轮恢复的修复波通常意味着实现者无法看到自己的问题——新鲜眼睛和能力提升一举两得。

**每轮，任一方式：** 实现者修复，重新运行涵盖修改代码的测试，并以简短汇报收束（不写报告文件）。复检之前，确认汇报包含涵盖测试、运行的命令和输出；在三者都存在时才做复检。在修复消息中命名涵盖测试文件——单行修复不需要整个套件。

**复检是范围的。** 运行 `bash scripts/review-package PLAN_FILE FIX_BASE HEAD`，其中 FIX_BASE 是上一轮复检看到的头部（第一轮就是整分支自审看到的头部），自己通读本轮修复 diff（清单见 [re-review-prompt.md](../re-review-prompt.md)），对每条未决发现裁决为已解决或未解决，并仅标记本轮修复 diff 中的新破坏。本轮修复 diff 中的新关键/重要破坏加入开放发现列表。范围外观察转到账本作为延后的次要——它们永远不扩展修复波。

**每轮之后，** 追加到账本：
`审查: 修复波 (<轮次>/3, <X> 已解决, <Y> 未决 — <发现一行摘要>; 提交 <a7>..<b7>)`

永远不要在控制器会话中自己修复发现——你的上下文保持干净用于协调，且控制器修复跳过复检。

**断路器。** 当三轮用满、复检仍有未决发现时，停止派遣。亲自裁决每个开放发现——你拥有实现者缺乏的计划和跨任务上下文：

- **发现是误报，或观点可争议：** 停放它——`任务 <N>: 停放 — <发现> — 裁决: <代码为何成立>`。收尾看到双方。
- **真实的，但没有下游构建它：** 同样停放它，带有裁决说它是真实的且延迟的。
- **真实且负载关键**——会破坏合并后的主分支，或它揭示计划缺陷：在最小更改上裁决以解除阻塞，账本为 `任务 <N>: 裁决: <发现> — <你决定什么及为什么>`，并把它带进收尾，通过 finishing-a-development-branch 呈现给你的（人类）搭档。停放结构故障无声地让每个依赖任务构建于它。仅在缺陷使每个前进路径成为猜测时停止。

仅在三轮用满后裁决。更早裁决以结束修复波是用不同名称的预判。每个裁决是账本条目——无声丢弃是禁止的。
