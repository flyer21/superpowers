# 写好代码（Writing Good Code）

**以下情形加载本参考：** 在 TDD 第 2 步（GREEN）编写让测试通过的实现代码，或在 REFACTOR 步骤清理代码时。

## 概述（Overview）

产品代码存在的理由有两个：让当前这批测试通过，并且让下一个人读得懂、改得动。TDD 循环把这些质量逐个逼出来——测试划定了行为的边界（正确性），GREEN 的纪律划定了代码的边界（最小），REFACTOR 的纪律负责其余的一切。

**优先级大致是：正确性 > 可读性/可维护性 > 性能/安全/扩展性。** 但具体场景会调整：底层库更看重性能和安全，业务系统更看重可读性和可维护性。优先级冲突时，先问你的搭档。

---

## 正确性（Correctness）

这是底线：代码再优雅，不正确就不是好代码。

- 满足需求，边界条件、异常情况、并发场景都正确。
- 数据一致、事务正确、必要时幂等。

在 TDD 里，正确性不是"我觉得对"，而是"测试说得清"。每一个声称的正确性——边界、异常、并发、幂等——都应当对应一个已经写就的测试；没有测试的正确性只是猜测。实现超出测试断言的部分，不受任何保护。

## 可读性（Readability）

- 命名见名知意，避免 `a`、`tmp`、`data2`。名字说行为，不说机制：`rejectsBlankEmail` 优于 `checkEmail`。测试名称已经定义了行为——实现里的命名照着它对齐。
- 函数短小、职责单一，控制流简单，少用多层嵌套。
- 格式统一，注释解释"为什么"，而不是重复"做了什么"。
- 代码本身尽量像文档，让人能快速看懂。

## 可维护性（Maintainability）

- 高内聚、低耦合，模块边界清晰。
- 遵循 SOLID、DRY、KISS、YAGNI 等原则，**但不教条**。
- 修改一个功能时，尽量只改一处，而不是牵一发而动全身。
- 避免全局状态、隐藏依赖、过度抽象和过度设计。

**重复不是"长得像的代码"，是"必须一起改的代码"。** 抽象要由重复来付账：没有第三处重复之前，不抽辅助函数、不建基类、不分层。**REFACTOR 的纪律：** 只改结构，不改行为；每一步重构之后立即跑测试，保持全绿。红了就撤回这一步——说明改过头了。

## 可测试性（Testability）

- 容易写单元测试、集成测试。
- 依赖可注入、可替换，关键逻辑尽量纯函数化。
- 测试覆盖核心路径、边界条件和错误分支。

测试难写 = 设计不清楚，要听测试的（详见 `SKILL.md`「卡住时」）。没有测试保护的代码，很难长期演进。

## 健壮性与可靠性（Robustness & Reliability）

- 输入校验、错误处理、失败快速（fail fast）。
- 不吞异常，错误信息有上下文。
- 资源正确释放：文件、连接、锁、内存。
- 超时、重试、熔断、降级、幂等按场景考虑。

注意 GREEN 的纪律：只有测试要求了这个错误分支，才写这个错误分支；每一条健壮性行为（重试几次、超时多长）都应该有一个测试说出它抓的断裂。

## 性能与效率（Performance & Efficiency）

- 选择合适的数据结构和算法。
- **避免过早优化，基于测量优化。**
- 关注内存、IO、网络、并发和数据库访问。
- 性能不是越快越好，而是满足需求且不牺牲可维护性。

"优化"没有测试护住就是赌博：先写一个能量化当前性能的基准测试，再动手，改完用同一个基准对比。没有基准的性能改动，属于 GREEN 阶段禁止的"顺手改进"。

## 安全性（Security）

- 输入验证、最小权限、防注入、防越权。
- 敏感数据加密、脱敏、安全存储。
- 管理依赖漏洞，不硬编码密钥。
- 安全标准随领域不同而不同，金融、医疗、基础设施要求更高。

## 可扩展性与可复用性（Extensibility & Reusability）

- 接口稳定，依赖抽象，符合开闭原则。
- 合适处配置化、插件化、模块化。
- 但不要为了"未来可能用到"而过度抽象。

**好代码是容易加功能，而不是现在就很复杂。** "框架/需求最终会需要这些"是 YAGNI——等那个测试出现时再写，那时你才知道它真正要什么。灵活性没有测试就是死重。

## 一致性与工程实践（Consistency & Engineering Practice）

- 遵循团队代码风格、命名约定、目录结构。
- 使用格式化、Lint、静态分析、CI/CD。
- 代码评审、版本控制、提交信息清晰。
- 文档说明架构、接口、部署和关键决策。

一个 PR 只解决一个问题：相邻的 bug、顺手的美化，都不要混进当前 diff——为它另写一个测试，下一轮循环处理。

## 可观测性（Observability）

- 关键路径有日志、指标、追踪。
- 日志有级别、上下文、可检索，不刷屏。
- 出问题时能快速定位，而不是靠猜。

## GREEN 阶段的最小性（Minimality in GREEN）

GREEN 阶段写的是"刚好通过"，不是"完整方案"。测试要求什么，就实现什么——每多写的一行，都是没有测试保护的负债。

**通用化要等第二个测试来要。** 只有一个测试时，返回字面量是合法的 GREEN：

```typescript
test('greets by name', () => {
  expect(greet('Ada')).toBe('Hello, Ada');
});

// ✅ 合法的 GREEN：字面量
function greet(name: string) {
  return 'Hello, Ada';
}
```

但字面量欠了一笔债：**下一个测试必须把它逼成真实现。** 只有一个测试却写出完整通用实现，和有了两个测试还在返回字面量，是同一种病——前者在替测试做主，后者在欺骗测试。

### 闸门函数（Gate Function）

```
写 GREEN 代码之前：
  重读这个测试断言的行为——不是你脑补的完整需求。

  每写一段实现，问：这段代码对应哪条断言？
    说不出来          → 删掉它
    "迟早用得上"      → YAGNI；等测试来要
    "顺手修了个 bug"  → 撤掉；为它另写一个测试

  收工之前：
    只有一个测试，实现却是通用的？
      要么退回字面量，要么再写一个能逼出通用性的测试。
```

## 常见的自我合理化（Common Rationalizations）

| 借口 | 现实 |
|--------|---------|
| "框架/需求最终会需要这些" | YAGNI。等那个测试出现时再写，那时你才知道它真正要什么。现在写的，到时候多半要改。 |
| "先把结构搭完整，逻辑随后填" | 这是实现先行，只是换了个说法。行为由测试逐个驱动，结构会自己长出来。 |
| "顺手把旁边的 bug 也修了" | 混合 diff。先写一个复现那个 bug 的测试，下一轮循环再修它。 |
| "这是最佳实践/设计模式" | 模式是重复出现后总结的，不是预先套用的。测试没要求的那一层间接性，就是成本。 |
| "多加个参数更灵活" | 灵活性没有测试就是死重。等第二个调用方带着第二个测试来要。 |
| "这里先优化一下性能" | 没有基准测量的优化是赌博。先写量化性能的测试。 |
| "最小实现太丑了" | 最小 ≠ 马虎。丑是 REFACTOR 阶段处理的事，且丑在"重复"上，不在"缺功能"上。 |
| "重构太小步了，太慢" | 一步跨大了测试变红，你要花更久才能定位。小步快跑才是快。 |
| "先这样，回头再改" | 没有"回头"。要么现在 REFACTOR 保持全绿，要么带着测试写下一个特性。 |

## 危险信号（Warning Signs）

- 实现里的分支比测试覆盖的行为多
- 函数签名里出现任何测试都没传入过的参数、选项、配置
- diff 触及了与本轮测试无关的文件，而且说不出理由
- 只有一个测试，实现却已经"通用"
- 抽象只有一个调用方、一个实现
- "为将来扩展预留"的接口、基类或回调
- 注释里写着 TODO 而没有任何对应的失败测试
- 重构之后没有立即运行测试
- 输出里有警告或报错，但"反正测试是绿的"
- 吞掉的异常、空 catch 块、"以后再处理"的错误分支
- 硬编码的密钥、路径、环境假设

**以上任何一条出现，都意味着代码超出了测试划定的边界，或正确性本身存疑。删掉多余的部分，回到 GREEN。**

## 速查表（Quick Reference）

| 当你…… | 就…… |
|-------------|-----|
| 写 GREEN 代码 | 只实现当前测试断言的行为，一行不多 |
| 只有一个测试却想写通用实现 | 退回字面量；用下一个测试去逼出通用性 |
| 想加测试没要求的参数/选项/分支 | 不加；等测试来要 |
| 发现相邻的 bug | 写一个复现测试放进待办，本轮继续 |
| 想抽取辅助函数/抽象 | 先数重复：不足两处，内联 |
| 想优化性能 | 先写基准测试，基于测量优化 |
| 写错误处理 | 不吞异常，错误信息带上下文；每个分支有测试 |
| 命名 | 对齐测试名称里的行为语言 |
| 做完任何一步重构 | 立即运行测试，红了就撤回 |
| 优先级拿不准 | 正确性优先；其余按场景问你的搭档 |
