# 系统化调试（Systematic Debugging）

## 概述（Overview）

**核心原则：** 永远先找到根因，再尝试修复。修症状就是失败。

**违反本流程的字面规定，就等于违背调试的精神。**

## 铁律（The Iron Law）

```
先调查根因，再谈修复（NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST）
```

如果你还没完成第一阶段，就不能提出修复方案。

## 何时使用（When to Use）

任何技术问题都适用：
- 测试失败
- 生产环境中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其是在以下情况使用：**
- 时间压力下（紧急情况最诱人去瞎猜）
- "就一个快速修复"看似显而易见
- 你已经试过多个修复
- 之前的修复没生效
- 你还没有完全理解这个问题

**以下情况不要跳过：**
- 问题看似简单（简单的 bug 也有根因）
- 你在赶时间（匆忙只会保证返工）
- 经理现在就要修好（系统化比反复折腾更快）

## 四个阶段（The Four Phases）

在进入下一阶段之前，你必须完成当前阶段。

### 第一阶段：根因调查（Phase 1: Root Cause Investigation）

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含精确的解决方案
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误代码

2. **稳定地复现**
   - 你能可靠地触发它吗？
   - 精确的步骤是什么？
   - 每次都发生吗？
   - 如果无法复现 → 收集更多数据，不要瞎猜

3. **检查最近的改动**
   - 什么改动可能导致这个问题？
   - Git diff、最近的提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，添加诊断性插桩：**
   ```
   针对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传播
     - 检查每一层的状态

   先运行一次以收集证据，看它在哪里中断
   然后分析证据，识别出故障组件
   然后深入调查那个具体组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第 3 层：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误深埋在调用栈中时：**

   完整的向后追踪技术见本目录下的 `root-cause-tracing.md`。

   **简版：**
   - 坏值从哪里起源？
   - 是谁用坏值调用了这里？
   - 一路向上追踪，直到找到源头
   - 修在源头，而不是修在症状

### 第二阶段：模式分析（Phase 2: Pattern Analysis）

**先找到模式，再修复：**

1. **找到可用的范例**
   - 在同一个代码库里定位相似的可用代码
   - 与坏代码相似、但能工作的代码是什么？

2. **与参考实现对照**
   - 如果是在实现某个模式，要完整地阅读参考实现
   - 不要略读——要逐行阅读
   - 在应用之前要充分理解这个模式

3. **找出差异**
   - 能工作的与坏掉的之间差在哪里？
   - 列出每一个差异，无论多小
   - 不要想当然地说"那个不可能有关系"

4. **理解依赖**
   - 它还需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 第三阶段：提出假设并测试（Phase 3: Hypothesis and Testing）

**科学方法：**

1. **形成单一假设**
   - 清楚地陈述："我认为 X 是根因，因为 Y"
   - 把它写下来
   - 要具体，不要含糊

2. **最小化地测试**
   - 做出尽可能小的改动来测试假设
   - 一次只改一个变量
   - 不要同时修多个东西

3. **继续之前先验证**
   - 起作用了吗？是 → 进入第四阶段
   - 没起作用？形成新的假设
   - 不要在原有修复上继续叠加

4. **当你不明白时**
   - 说"我不理解 X"
   - 不要装懂
   - 请求帮助
   - 继续研究

### 第四阶段：实施（Phase 4: Implementation）

**修复根因，而不是修复症状：**

1. **创建失败的测试用例**
   - 尽可能简单的复现
   - 尽可能做成自动化测试
   - 如果没有框架，就用一次性测试脚本
   - 修复之前必须要有
   - 使用 `superpowers:test-driven-development` 技能来编写规范的失败测试

2. **实施单一修复**
   - 针对已确认的根因
   - 一次只改一处
   - 不要做"顺手"的改进
   - 不要捆绑重构

3. **验证修复**
   - 现在测试通过了吗？
   - 没有其他测试被破坏吗？
   - 问题真的解决了吗？
   - 在声称成功之前，使用 `superpowers:verification-before-completion` 技能

4. **如果修复不起作用**
   - 停下来（STOP）
   - 数一数：你试过几个修复了？
   - 如果 < 3：回到第一阶段，用新信息重新分析
   - **如果 ≥ 3：停下来，质疑架构（下面的第 5 步）**
   - 在没有架构讨论的情况下，不要尝试第 4 个修复

5. **如果 3+ 个修复都失败：质疑架构**

   **表明架构问题的模式：**
   - 每个修复都在不同位置暴露出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每个修复都在别处制造出新症状

   **停下来质疑根本：**
   - 这个模式在根本上可靠吗？
   - 我们是不是"纯靠惯性死撑着"？
   - 应该重构架构，还是继续修症状？

   **在尝试更多修复之前，与你的人类搭档讨论**

   这不是假设失败——这是架构选错了。

## 危险信号——停下来，走流程（Red Flags - STOP and Follow Process）

如果你发现自己冒出这些念头：
- "先快速修一下，之后再调查"
- "就试试改一下 X，看能不能行"
- "多做几处改动，然后跑测试"
- "跳过测试，我手动验证"
- "大概就是 X，让我修它"
- "我没有完全理解，但这个也许能行"
- "模式说应该这样，但我要改成另一种做法"
- "主要问题如下：[不经过调查就列出修复]"
- 在追踪数据流之前就提出解决方案
- **"再试一次修复"（当已经试过 2+ 次时）**
- **每个修复都在不同位置暴露出新问题**

**以上所有情况都意味着：停下来。回到第一阶段。**

**如果 3+ 个修复都失败：** 质疑架构（见第四阶段第 5 步）

## 你的搭档发出"你做错了"的信号

**留意这些纠偏话语：**
- "那不是没发生吗？"——你没验证就自行假设了
- "它会向我们展示……？"——你本该添加证据收集
- "别瞎猜"——你在不理解的情况下提出修复
- "深度思考一下"——要质疑根本，而不只是症状
- "我们卡住了？"（沮丧）——你的方法不奏效

**当你看到这些时：** 停下来。回到第一阶段。

## 常见的自我合理化

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要流程" | 简单的问题也有根因。对简单 bug，流程也很快。 |
| "情况紧急，没时间走流程" | 系统化调试比瞎猜乱试更快。 |
| "先试这个，之后再调查" | 第一个修复定下基调。一开始就要做对。 |
| "确认修复有效后我再写测试" | 没经过测试的修复立不住。先写测试才能证明它。 |
| "一次性多个修复省时间" | 无法隔离出是哪个起效。还会引入新 bug。 |
| "参考太长，我改改模式就行" | 一知半解注定出 bug。要完整阅读。 |
| "我看到问题了，让我修" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（2+ 次失败后） | 3+ 次失败 = 架构问题。要质疑模式，别再修了。 |

## 快速参考（Quick Reference）

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、复现、查改动、收集证据 | 理解是什么和为什么 |
| **2. 模式** | 找可用范例、对照比较 | 找出差异 |
| **3. 假设** | 形成理论、最小化测试 | 假设被证实或形成新假设 |
| **4. 实施** | 建测试、修复、验证 | bug 解决、测试通过 |

## 当流程揭示出"没有根因"时

如果系统化调查揭示问题确实是环境性的、时间依赖性的、或外部的：

1. 你已经走完了流程
2. 记录你调查过什么
3. 实施合适的应对（重试、超时、错误提示）
4. 为将来调查添加监控/日志

**但是：** 95% 的"没有根因"案例其实是调查不完整。
