# 接收代码评审反馈（Code Review Reception）

## 概述（Overview）

代码评审要求的是技术评估，而不是情绪表演。

**核心原则：** 先核实，再实施。先提问，再假设。技术正确性优先于社交上的舒服。

## 回应模式（The Response Pattern）

```
收到代码评审反馈时（WHEN receiving code review feedback）：

1. 阅读（READ）：完整读完反馈，不急着反应
2. 理解（UNDERSTAND）：用自己的话复述需求（或提问）
3. 核实（VERIFY）：对照代码库的现实进行核查
4. 评估（EVALUATE）：对这个代码库而言技术上是否成立？
5. 回应（RESPOND）：技术性确认，或基于理由的反驳
6. 实施（IMPLEMENT）：一次一项，逐项测试
```

## 被禁止的回应（Forbidden Responses）

**绝不（NEVER）：**
- "你说得太对了！"（明确违反指令文件）
- "好观点！" / "很棒的反馈！"（表演式）
- "我现在就实现它"（核实之前）

**而要（INSTEAD）：**
- 复述技术需求
- 提出澄清性问题
- 如果建议是错的，用技术理由反驳
- 直接开始干活（行动 > 言辞）

## 处理含糊的反馈（Handling Unclear Feedback）

```
如果任一条目含糊不清（IF any item is unclear）：
  停下（STOP）——先什么都别实施
  就含糊的条目提问（ASK）请求澄清

为什么（WHY）：各条目可能是互相关联的。理解不完整 = 错误的实现。
```

**示例：**
```
你的人类搭档（your human partner）："修复 1-6"
你理解了 1、2、3、6。对 4、5 不清楚。

❌ 错误：现在就实施 1、2、3、6，之后再问 4、5
✅ 正确："我理解了条目 1、2、3、6。在继续之前需要澄清 4 和 5。"
```

## 按反馈来源区别处理（Source-Specific Handling）

### 来自你的人类搭档
- **可信赖（Trusted）**——理解之后即可实施
- **范围不清时仍要问**（Still ask）
- **不要表演式附和**（No performative agreement）
- **直接行动**或技术性确认

### 来自外部评审者
```
在实施之前（BEFORE implementing）：
  1. 核查：对这个代码库而言技术上正确吗？
  2. 核查：会破坏现有功能吗？
  3. 核查：当前实现这么写的原因是什么？
  4. 核查：在所有平台 / 版本上都能工作吗？
  5. 核查：评审者了解完整上下文吗？

如果建议看起来是错的（IF suggestion seems wrong）：
  用技术理由反驳（Push back）

如果不容易核实（IF can't easily verify）：
  直说："没有 [X] 我没法核实这个。我该[调查 / 询问 / 继续]吗？"

如果与你的人类搭档先前的决定冲突（IF conflicts）：
  先停下，与你的人类搭档讨论
```

**你的人类搭档的规矩：** "外部反馈——要保持怀疑，但要仔细核查"

## 对"专业化"特性的 YAGNI 检查（YAGNI Check for "Professional" Features）

```
如果评审者建议"要做得正规"（IF reviewer suggests "implementing properly"）：
  在代码库里 grep 实际的调用情况

  如果没人用：这个接口没被调用。删掉它吗（YAGNI）？
  如果有人在用：那就正规地实现
```

**你的人类搭档的规矩：** "你和我都向搭档汇报。如果我们不需要这个功能，就别加。"

## 实施顺序（Implementation Order）

```
对多条反馈（FOR multi-item feedback）：
  1. 先把任何含糊之处澄清（FIRST）
  2. 然后按此顺序实施：
     - 阻塞性问题（破坏功能、安全问题）
     - 简单修复（拼写错误、导入问题）
     - 复杂修复（重构、逻辑）
  3. 逐项单独测试每个修复
  4. 确认没有回归
```

## 何时该反驳（When To Push Back）

出现以下情况时反驳：
- 建议会破坏现有功能
- 评审者缺少完整上下文
- 违反 YAGNI（未使用的功能）
- 对本技术栈而言技术上不正确
- 存在遗留 / 兼容性原因
- 与你的人类搭档的架构决策冲突

**如何反驳：**
- 用技术理由，而不是防御姿态
- 问具体的问题
- 引用能工作的测试 / 代码
- 涉及架构问题时把搭档拉进来

**如果你不习惯当面反驳：** 说出那层顾虑，然后把你看出的问题告诉你的搭档。他们会欣赏你的坦诚。

## 认可正确的反馈（Acknowledging Correct Feedback）

当反馈确实正确时：
```
✅ "已修复。[简要说明改了什么]"
✅ "好眼力——[具体问题]。已在[位置]修复。"
✅ [直接修好，让代码自己说话]

❌ "你说得太对了！"
❌ "好观点！"
❌ "谢谢指出！"
❌ "感谢[任何东西]"
❌ 任何表达感谢的话
```

**为什么不要道谢：** 行动胜于言语。直接修掉即可。代码本身就表明你听进了反馈。

**如果你发现自己正要写"谢谢"：** 删掉它。改为陈述修复内容。

## 优雅地纠正你的反驳（Gracefully Correcting Your Pushback）

如果你反驳过、但结果是自己错了：
```
✅ "你是对的——我查了 [X]，它确实 [Y]。现在开始实施。"
✅ "核实过了，你是对的。我最初的判断错了，因为[原因]。正在修复。"

❌ 长篇道歉
❌ 为自己当初的反驳辩护
❌ 过度解释
```

如实地陈述纠正，然后继续往前走。

## 常见错误（Common Mistakes）

| 错误（Mistake） | 修正（Fix） |
|---------|-----|
| 表演式附和 | 陈述需求，或直接行动 |
| 盲目实施 | 先对照代码库核实 |
| 批量修改不做测试 | 一次一项，逐项测试 |
| 假定评审者一定对 | 先检查是否会破坏功能 |
| 回避反驳 | 技术正确性 > 舒适感 |
| 部分实现 | 先澄清所有条目 |
| 无法验证仍继续推进 | 说明局限，请求方向 |

## 真实示例（Real Examples）

**表演式附和（不好）：**
```
评审者："删掉遗留代码"
❌ "你说得太对了！我这就去删……"
```

**技术核实（好）：**
```
评审者："删掉遗留代码"
✅ "查一下……构建目标是 10.15+，而这个 API 需要 13+。为了向后兼容必须保留
遗留代码。当前实现的 bundle ID 是错的——要么修它，要么放弃对 13 以下的支持？"
```

**YAGNI（好）：**
```
评审者："用数据库、日期筛选、CSV 导出实现正规的指标追踪"
✅ "grep 过代码库——没有任何东西调用这个接口。要删掉它吗（YAGNI）？还是说
有我漏掉的调用？"
```

**含糊条目（好）：**
```
你的人类搭档（your human partner）："修复条目 1-6"
你理解了 1、2、3、6。对 4、5 不清楚。
✅ "理解了 1、2、3、6。在实施之前需要对 4 和 5 的澄清。"
```

## GitHub 评论线程回复（GitHub Thread Replies）

当回复 GitHub 上的行内评审评论时，请回复在该评论的线程里
（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），
而不要作为 PR 的顶层评论发布。
