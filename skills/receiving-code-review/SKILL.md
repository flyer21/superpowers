# 代码审查接收

## 概述

代码审查需要技术评估，而不是情感表演。

**核心原则：** 在实施之前验证。在假设之前询问。技术正确性高于社交舒适度。

## 响应模式

```
当收到代码审查反馈时：

1. 阅读：完整阅读反馈而不做出反应
2. 理解：用自己的话重述需求（或询问）
3. 验证：对照代码库现实检查
4. 评估：对这个代码库在技术上合理吗？
5. 响应：技术确认或有理有据的反对
6. 实施：一次一项，每项测试
```

## 禁止的响应

**永远不要：**
- "你完全正确！"（明确违反指令文件）
- "好观点！"/ "出色的反馈！"（表演式）
- "让我现在实施"（在验证之前）

**而是：**
- 重述技术需求
- 提出澄清问题
- 如果错了，用技术推理反对
- 直接开始工作（行动 > 言语）

## 处理不清楚的反馈

```
如果任何项目不清楚：
  停止 - 还不要实施任何东西
  就不清楚的项目请求澄清

为什么：项目可能相关。部分理解 = 错误实施。
```

**示例：**
```
你的（人类）搭档："修复 1-6"
你理解 1,2,3,6。不清楚 4,5。

❌ 错误：现在实施 1,2,3,6，稍后询问 4,5
✅ 正确："我理解项目 1,2,3,6。在继续之前需要对 4 和 5 进行澄清。"
```

## 特定来源的处理

### 来自你的（人类）搭档
- **可信** - 理解后实施
- **仍然询问** 如果范围不清楚
- **不要表演式同意**
- **跳到行动** 或技术确认

### 来自外部审查者
```
在实施之前：
  1. 检查：对这个代码库在技术上正确吗？
  2. 检查：破坏现有功能吗？
  3. 检查：当前实现的原因是什么？
  4. 检查：在所有平台/版本上工作吗？
  5. 检查：审查者理解完整上下文吗？

如果建议看起来错误：
  用技术推理反对

如果无法轻松验证：
  说出来："没有 [X] 我无法验证这个。我应该 [调查/询问/继续] 吗？"

如果与你的（人类）搭档的先前决定冲突：
  停下来先与你的（人类）搭档讨论
```

**你的（人类）搭档的规则：** "外部反馈——保持怀疑，但仔细检查"

## 对"专业"功能的 YAGNI 检查

```
如果审查者建议"正确实施"：
  grep 代码库查找实际使用

  如果未使用："这个端点没有被调用。删除它（YAGNI）？"
  如果使用：那么正确实施
```

**你的（人类）搭档的规则：** "你和审查者都向我汇报。如果我们不需要这个功能，不要添加它。"

## 实施顺序

```
对于多项目反馈：
  1. 首先澄清任何不清楚的项目
  2. 然后按此顺序实施：
     - 阻塞问题（破坏、安全）
     - 简单修复（拼写错误、导入）
     - 复杂修复（重构、逻辑）
  3. 单独测试每个修复
  4. 验证无回归
```

## 何时反对

当以下情况时反对：
- 建议破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对此堆栈在技术上不正确
- 存在遗留/兼容性原因
- 与你的（人类）搭档的架构决定冲突

**如何反对：**
- 使用技术推理，而不是防御性
- 提出具体问题
- 引用工作的测试/代码
- 如果是架构问题，让你的（人类）搭档参与

**如果你不舒服公开反对：** 说出这种紧张感，然后告诉你的搭档你看到的问题。他们会欣赏你的诚实。

## 确认正确的反馈

当反馈正确时：
```
✅ "已修复。[更改的简要描述]"
✅ "好发现 - [具体问题]。已在 [位置] 修复。"
✅ [直接修复并在代码中展示]

❌ "你完全正确！"
❌ "好观点！"
❌ "谢谢你发现那个！"
❌ "谢谢 [任何内容]"
❌ 任何感谢表达
```

**为什么不感谢：** 行动说话。直接修复。代码本身表明你听到了反馈。

**如果你发现自己要写"谢谢"：** 删除它。改为说明修复。

## 优雅地纠正你的反对

如果你反对但错了：
```
✅ "你是对的 - 我检查了 [X] 它确实 [Y]。现在实施。"
✅ "验证了这个并且你是正确的。我最初的理解错了因为 [原因]。正在修复。"

❌ 长道歉
❌ 防御为什么你反对
❌ 过度解释
```

事实性地说明更正并继续。

## 常见错误

| 错误 | 修复 |
|------|------|
| 表演式同意 | 说明需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量而不测试 | 一次一项，每项测试 |
| 假设审查者正确 | 检查是否破坏东西 |
| 避免反对 | 技术正确性 > 舒适度 |
| 部分实施 | 先澄清所有项目 |
| 无法验证，仍然继续 | 说明限制，请求指导 |

## 真实示例

**表演式同意（坏）：**
```
审查者："删除遗留代码"
❌ "你完全正确！让我删除那个..."
```

**技术验证（好）：**
```
审查者："删除遗留代码"
✅ "检查中... 构建目标是 10.15+，这个 API 需要 13+。需要遗留以向后兼容。当前实现有错误的 bundle ID - 修复它还是放弃 13 之前支持？"
```

**YAGNI（好）：**
```
审查者："用数据库、日期过滤器、CSV 导出实现正确的指标跟踪"
✅ "Grep 代码库 - 没有东西调用这个端点。删除它（YAGNI）？还是有我遗漏的使用？"
```

**不清楚项目（好）：**
```
你的（人类）搭档："修复项目 1-6"
你理解 1,2,3,6。不清楚 4,5。
✅ "理解 1,2,3,6。在实施之前需要对 4 和 5 进行澄清。"
```
