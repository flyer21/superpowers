# 多阶段设计（Multi-Phase Designs）设计文档

日期：2026-09-19
状态：待审阅

## 问题

Superpowers 的工作流假设一个目标可以用**一份**设计（规格说明）承载。当一个目标太大、一个设计装不下时，现有指引（brainstorming 的"分解成子项目"）只覆盖了**相互独立的子系统**——各自独立设计、互不依赖。

未被覆盖的场景是**顺序依赖的阶段**：阶段 N+1 的设计要等阶段 N 建成并验证后才能做（学习驱动的渐进式设计）。典型例子：

- 先建 MVP 验证核心假设，再基于使用反馈设计扩展能力
- 先建数据层并验证性能，再基于实测设计上层功能
- 先建基础设施，后续功能的设计取决于基础设施实际暴露的接口形态

当前技能链在这类场景下断裂：

1. brainstorming 只有"独立子系统拆分"指引，没有顺序阶段的概念
2. writing-plans 的范围检查同样只拆独立计划
3. executing-plans / subagent-driven-development 完成后直接进入 finishing-a-development-branch，没有任何机制回到下一阶段的设计——闭环缺失

## 目标

当目标太大、一个设计无法承载时，支持按**顺序阶段**推进：每个阶段走自己的 规格 → 计划 → 实施 循环，阶段之间用一份轻量路线图串联，收尾后自动衔接下一阶段的设计。

## 非目标

- 不改变独立子系统拆分的现有行为
- 不引入新脚本、新依赖或新技能
- 不重构任何技能的整体结构（符合 AGENTS.md 对行为塑造内容的修改门槛）
- 不在路线图中承载设计细节——路线图只管阶段边界

## 方案概述

**增量锚点式（方案 A）**：路线图作为一种轻量新文档类型，在 5 个现有技能中各做小节级改动，不动任何技能的整体结构。每个阶段内部仍走完整的架构级 规格 → 计划 → 实施 循环；多阶段只是循环之间的编排层。

被否决的备选：方案 B（brainstorming 新增第四条"多阶段"路径、各技能显式建模阶段状态机）——需要重构 brainstorming 的核心三路径结构，正是 AGENTS.md 警告需要大量 eval 证据的改动，且与 task-brief 脚本已有的计划内阶段标题能力重复。

## 详细设计

### 1. 路线图文档（新文档类型）

- **位置：** `docs/superpowers/roadmaps/YYYY-MM-DD-<topic>-roadmap.md`（用户对位置的偏好覆盖此默认值）
- **定位：** 轻量编排文档，不是规格。只含阶段边界，不含设计细节。
- **模板：**

```markdown
# [主题] 路线图

**目标（Goal）：** [整个多阶段工作要达成什么——一段话]

**为何分阶段（Why Phases）：** [哪些设计决策被延后、为什么一个设计承载不了]

## 阶段列表（Phases）

| 阶段 | 名称 | 目标（一句话） | 依赖 | 验收标准 | 状态 |
|------|------|----------------|------|----------|------|
| 1 | … | … | — | [何时算"建成"] | 待开始 |

状态取值：待开始 / 设计中 / 执行中 / 已完成

## 被延后的设计决策（Deferred Decisions）

- [决策点] — 预计在阶段 N 解决

## 修订记录（Revisions）

- YYYY-MM-DD 阶段 N 完成：[基于学习对后续阶段的修订]
```

### 2. brainstorming 改动

改动位置："理解想法"的范围评估段（现为"如果请求描述的是多个相互独立的子系统……"）。

**2a. 两种分解。** 把现有指引扩展为两种：

- **独立子系统**（现有，不变）：组成部分相互独立，可并行设计。拆成子项目，各自走 规格 → 计划 → 实施。
- **顺序阶段**（新增）：后期阶段的设计依赖前期阶段**建成并验证的结果**。先产出路线图，再逐阶段推进。判断信号：用户说"先……再基于……"、"MVP 之后看情况"、或阶段 N+1 的关键设计决策在阶段 N 建成前无法做出。

两种情况可能混合：路线图中的阶段可以标注"（含独立子系统，另行拆分）"。

**2b. 路线图头脑风暴。** 识别出顺序阶段后：

1. 一次一个问题，澄清：整体目标、阶段的自然边界（哪些能力必须先存在）、每阶段的验收标准
2. 呈现路线图（聊天内，按复杂度缩放），获得批准
3. 写入路线图文档并提交到 git
4. 然后仅对**阶段 1** 走正常架构级流程；其规格头部注明"路线图：<路径>（阶段 1：<名称>）"

**2c. 后续阶段的设计。** 阶段 N（N>1）的头脑风暴开始时，**必须**先回读路线图 + 阶段 1..N-1 的规格与建成成果。允许基于学习修订本阶段范围——修订必须写进路线图的"修订记录"，并把受影响后续阶段的描述更新。被延后到本阶段的设计决策现在正式进入设计。

**2d. 规格自审的范围检查**加一条：规格是否聚焦到本阶段，而不是整个路线图（整条路线图的内容出现在一份规格里 = 需要再分解或回到路线图）。

### 3. writing-plans 改动

**3a. 范围检查**（现为"如果规格说明涵盖多个相互独立的子系统……"）区分两种拆分：

- 独立子系统 → 多份独立计划（现有，不变）
- 顺序阶段 → **每阶段一份计划**。计划必须注明所属路线图与阶段号。不允许一份计划横跨多个路线图阶段——阶段间的衔接是路线图的职责，不是计划的职责

**3b. 计划头部模板**新增可选字段（位于"规格说明"之后）：

```markdown
**路线图（Roadmap）：** <路线图路径>（阶段 N：<阶段名称>）
```

规格来自路线图时**必填**；否则整个字段省略（不写"无"）。

### 4. executing-plans / subagent-driven-development 改动

- **executing-plans 第 3 步"完成开发"**：进入 finishing-a-development-branch 的交接语中，若计划头部有路线图字段，附上路线路径与阶段号——"我正在用 finishing-a-development-branch 技能来完成这份工作（路线图 <path>，阶段 N）。"
- **subagent-driven-development** 在整分支自审完成、转入 finishing 的交接处同样传递路线图路径与阶段号

传递的目的是让 finishing 的路线图检测有明确的检测对象，避免扫描猜测。

### 5. finishing-a-development-branch 改动

新增**第 7 步：路线图检测（Roadmap Check）**，位于第 6 步"清理工作区"之后：

- 现有第 1-6 步的行为**零变化**，菜单不变
- 执行完用户选择的整合选项后，检查调用方传递的路线图路径（以及路线图中的阶段状态）
- 若路线图存在**未完成阶段**：报告并等待用户决定，不自动开工：

  > 路线图 `<path>` 中还有未完成阶段。下一阶段是"<阶段 N+1 名称>"。要现在开始它的头脑风暴吗？

  用户同意 → 调用 brainstorming 技能开始阶段 N+1（它会先回读路线图，见 2c）；拒绝 → 结束，行为与现状一致
- 若无路线图或所有阶段已完成 → 建议用户归档/更新路线图状态（阶段 N 标记"已完成"），结束

**阶段状态更新时机：** 路线图随阶段 1 的分支一起提交（在阶段工作区内）；整合（合并/PR）后路线图已落到基分支。每个阶段在 finishing 的路线图检测步骤中、于基分支上把本阶段标记为"已完成"并提交，再做下一阶段提示——不依赖已清理的工作区。

### 6. 各技能改动的完整清单

| 技能 | 改动 | 性质 |
|------|------|------|
| brainstorming | 范围评估段扩展两种分解；路线图头脑风暴；后续阶段回读；自审范围检查加一条 | 小节级 |
| writing-plans | 范围检查区分两种拆分；计划头部加可选"路线图"字段 | 小节级 |
| executing-plans | 第 3 步交接语传递路线图 | 一句话 |
| subagent-driven-development | finishing 交接处传递路线图 | 一句话 |
| finishing-a-development-branch | 新增第 7 步路线图检测 | 新增小节 |

## 错误处理

- **路线图与实际进度脱节**（阶段状态未更新、文档与代码不符）：阶段 N 头脑风暴回读时发现不一致 → 停下来向用户指出并确认真实状态，先修路线图再继续
- **修订导致阶段重排/废弃**：写入修订记录，原阶段标记状态变更（如"已废弃"），不删除历史行
- **计划横跨多阶段**（writing-plans 范围检查失败）：要求拆分，回到路线图确认阶段边界
- **finishing 未收到路线图路径但路线图存在**：不扫描猜测；可提示"检测到 docs/superpowers/roadmaps/ 下有路线图，本次工作是否属于某个阶段？"由用户确认

## 测试与验收

1. 纯技能文档改动，无新脚本、无依赖 → `tests/` 基础设施测试预期不受影响；提交前完整跑一遍确认
2. 按 AGENTS.md 要求，实施使用 `superpowers:writing-skills` 技能开发
3. Eval 验收（在 evals/ 中，遵循 superpowers-evals 流程）：
   - **验收 1（路线图自动产出）：** 给一个明确需要顺序阶段的大目标，会话自动产出路线图文档，而不是单一规格
   - **验收 2（阶段闭环）：** 阶段 1 执行收尾后，自动提示进入阶段 2 的头脑风暴
   - **验收 3（无回归）：** 普通单阶段目标（有界/架构级）的行为与现状一致——不产生路线图、不出现阶段提示
4. 对抗性压测：多会话验证合理化路径（如"我直接把阶段 2 一起设计了"被正确拒绝）
